# AAB助手：搭建与实现简介

本文依据交付包中可检查的代码，按实现依赖整理搭建顺序，说明如何形成目前的软件；不代表原作者的实际开发时间线。这里描述的是架构与实现概要，现有交付包包含编译后的前端，并非完整的前端开发源码仓库。

## 一、软件的组成

本软件基于 Partner Agent 本机桌面工作台整理，将项目选择、模型配置、技能模块、任务执行、日志查看和构建产物整合到一个界面中。GP打包是其中一个模块，负责组织 Android / Unity 项目的检查、编译和 AAB 交付。最终编译由本机工具链完成。

主要层次为：Electron 桌面窗口 → React 前端 → Node.js 本地接口 → 任务与技能模块 → OpenCode / 构建工具链。
SQLite 保存本地任务和设置；技能包保存模块清单、操作说明、脚本与资源。

## 二、按步骤搭建

### 第一步：搭建桌面外壳

使用 Electron 创建应用窗口。`desktop/main.cjs` 启动本地后端，等待健康检查通过，再加载工作台页面。窗口启用上下文隔离，前端不直接获得完整的系统执行能力；需要的桌面功能通过受控接口连接。

### 第二步：实现本地服务和数据保存

`server/index.js` 启动 Node.js 服务，`server/app-local.js` 提供工作台初始化、工程检查、设置、任务和技能包等接口。服务监听本机回环地址，并检查请求来源和本地操作标记。

`server/store.js` 使用 SQLite 保存数据，迁移模块负责建立和升级数据表。启动时恢复被中断的任务状态，使用户能够查看历史进度。

### 第三步：制作工作台界面

前端使用 React，发布文件位于 `dist/`。界面通过本地接口获取模块、任务、模型设置和引擎状态，并组织成工作台、GP打包、技能包管理与设置等页面。用户选择工程并提交参数后，由后端执行实际操作。

### 第四步：将功能做成技能模块

每个模块通过 `manifest.json` 声明标识、版本、类型、参数和技能文件位置。`SKILL.md` 与 `references/` 描述处理步骤，`scripts/` 和 `assets/` 提供执行脚本及资源。

`server/plugins.js` 发现模块，包安装和仓库管理模块负责导入、校验、更新及恢复。当前包已有 GP打包、多个 SDK 接入模块、数据同步及网站生成模块。外部 gp-build ZIP 是模块交付格式，不是独立桌面窗口。

### 第五步：接入模型和任务执行器

设置模块保存模型连接配置。`server/engine.js` 通过 OpenCode SDK 启动并连接本机 OpenCode 服务，建立会话、提交任务并接收事件。`server/tasks.js` 组织任务状态、日志、取消和产物信息。任务根据需要调用模型或专用执行逻辑；模型服务连接仍需用户自己的有效配置。

### 第六步：实现 GP 打包流程

用户在界面选择工程目录，输入版本号、Version Code，以及需要的模块或 Release 变体。后端校验参数，识别项目，并检查构建所需的环境与资源。

Android 构建逻辑主要位于 `server/gp-build.js`；Unity 游戏相关处理由 `gp-game`、`unity-preparation` 等模块协同完成。程序结合项目实际结构处理 Gradle、Unity 原生编译任务和必要依赖，再收集编译结果与诊断信息。

流程为：选择工程 → 检查参数与环境 → 准备项目 → 编译并查看诊断 → 用户确认 → 生成 Release AAB → 收集产物。

编译与最终打包分阶段执行：尚未确认时，构建逻辑阻止最终打包任务；确认有效后才继续生成 AAB。缺少签名、依赖、工具链或有效模型配置时，需要先补齐相应条件。

### 第七步：整理为公开版

启动后直接进入工作台，使用固定的本机工作区身份来关联任务。模型设置、技能包管理及打包入口可在本机使用，无需登录。

公开版采用独立的数据目录，与旧版记录分开保存，并停用旧版更新安装通道。打包确认、本机请求检查和凭据保护等执行约束继续生效。

### 第八步：封装与验证

将桌面入口、本地服务、前端发布文件、模块和运行组件一起封装进 `.app`，再制作 ZIP。修改应用内部文件后重新签名，并检查签名及压缩包完整性。

本次已验证本地启动、工作台初始化、设置保存、模块刷新、技能包管理接口和 GP打包参数校验。仍需使用真实工程完成端到端 AAB 构建，并在目标 macOS 设备上做图形界面验收。正式公开分发还需 Apple 开发者签名与公证。

### 第九步：改造为深蓝色横向操作台

先保留完整原包备份，再在副本上调整已编译 React 界面的布局：全局导航移到顶部，GP 配置横向排列，历史记录置于左侧，右侧显示进度、对话、日志和文件。原有事件处理函数和请求参数保持不变；“开始编译”移到标题区后仍关联原来的表单，确认操作仍受原任务状态控制。

基础样式统一为深蓝色，并在 `dist/assets/navy-horizontal.css` 中维护新布局、焦点提示、窄窗口适配和状态颜色。真实前端使用隔离的模拟任务验证操作，再打开桌面程序检查外观。测试数据不进入发行包。

### 第十步：处理可移动路径与修复工具

桌面入口通过自身位置寻找后端和内置运行组件，通过当前用户的系统数据目录保存配置。修复应用通过自身位置寻找同目录主应用，补充系统和用户应用目录查找，并支持手动选择。备用 shell 脚本递归检查和清除目标应用的隔离标记；各路径正确处理中文及空格。

将主应用显示名改为“AAB助手”，发行目录改为“aab自动打包软件”，保留兼容旧公开版的个人数据目录。发布前重新签名，压缩时保留应用权限、链接与资源信息。

## 三、后续维护

界面功能应在完整前端源码仓库中修改后重新构建；后端功能修改对应 `server/` 模块；技能流程更新对应技能包及版本。每次发布需验证模块兼容性、任务恢复、构建产物和签名完整性，避免将私钥、API Key 或用户工程数据装入公开包。

## 四、此次命名和平台范围

本次发行名称为“AAB助手”，入口与修复工具已同步更名。现有包仍为 macOS x86_64 程序，未交付 Windows 可执行版；Windows 的必要适配工作与 iOS 的 Mac 依赖见 [发行说明](DISTRIBUTION_README.md)。更名继续沿用公开版本机数据目录。
