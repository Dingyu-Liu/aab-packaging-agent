# 启动 Loading 与刘海安全区

这是本用户 01 系列的默认显示约定。当前任务已有不同的设计或网页全屏契约时，按用户的明确要求适配；不要把这套外观强加给无关项目。仅要求安全区适配时修改相关布局，不自动扩展为整个 Loading 状态机重构。是否构建、安装或做真机测试仍以本次任务授权为准。

## 按阶段控制方向

本用户 01 系列默认采用以下方向，用户明确指定其他方案时以本次要求为准：

| 阶段 | 默认方向 |
|---|---|
| 系统启动页 | `Portrait` 竖屏，从首帧开始 |
| ATT、SDK、归因与入口请求的 Loading | `Portrait` 竖屏 |
| 网页加载与默认页面 | `Portrait` 竖屏，不继承游戏横屏或自动旋转 |
| 网页已显示且收到有效 H5 方向指令 | 按协议切换；恢复前台时保留该网页当前方向模式 |
| 进入失败回退分支 | 保留遮罩，恢复原生游戏方向及开关，等真实布局就绪 |
| 原生游戏可见 | 使用游戏原有方向；横屏游戏恢复横屏，竖屏游戏保持竖屏，AutoRotation 游戏恢复原有允许范围 |

“保留原生横屏”只描述回退游戏的契约，不能扩大为全程横屏。用户反馈“现在是横屏”时，将它与当前阶段的预期对照排查；只有明确要求更改方向时才修改产品约定。

默认网页竖屏时保留既有且已确认的 H5 按钮、别名和回执。收到契约内的显式方向请求后允许切换；不能把启动竖屏实现为全程固定 Portrait 并拒绝网页横屏，也不能为修按钮给默认网页无条件开启 AutoRotation。仅在用户明确要求始终锁竖并禁用网页方向功能时实施永久限制。实际按钮链路见 [网页方向契约](webview-orientation.md)。

### 在覆盖启动方向前保存游戏契约

- 从原始 PlayerSettings 或游戏声明配置捕获原方向及四个自动旋转开关。若 iOS 导出临时改为 `Portrait`，把捕获值独立写入随包配置（例如自定义 Info.plist 字典），并在运行期读取。**运行期 Awake/Begin 读到的 Portrait 可能已经是启动覆盖值，不能再次保存为游戏原方向。**
- 一键脚本、实际 Unity 导出菜单和交付使用同一阶段规则。构建侧、启动配置、Unity 与 UIKit 控制器要让启动首帧就支持/选择竖屏；只等 C# 启动后调用 `Screen.orientation = Portrait`，不能证明系统启动页和原生 Loading 已竖屏。
- 核对 Info.plist 通用/设备专用方向键、AppDelegate 按窗口返回的允许 mask 与真实宿主控制器；有效允许范围要覆盖已支持的网页指令和游戏回退，启动期选择竖屏。使用 AppDelegate 动态返回 mask 时，启动配置与网页运行期 mask 分别核对，不能只凭 plist 中的 Portrait 判断网页始终锁定。静态配置或代理若把运行期有效范围永久限制为 Portrait，仅修改方向分发函数仍无法修好横屏。
- 进入原生分支时先使网页旧方向回调失效，解除网页阶段的 UIKit 方向限制，再恢复游戏的方向及全部开关；等 Unity 尺寸、控制器 mask 与实际窗口方向一致后揭开游戏。保留实际超时及失败记录，不用固定延时当作已完成旋转的证据。
- 临时修改导出设置时在 `finally` 中还原源工程，包括异常退出路径。源工程保留游戏原设置，与 App 首帧竖屏启动配置分别核对。

### 早期布局的启动崩溃

在 `preStartUnity` 等早期钩子挂 Loading 时，先核对该 Unity 版本的初始化顺序。若键盘仍将在此钩子之后初始化，强制对 Unity 根视图调用 `layoutIfNeeded` 可能经 `UnityView.layoutSubviews` 提前创建键盘，随后触发 `[KeyboardDelegate Initialize] called after creating keyboard` 断言。可请求后续布局（如 `setNeedsLayout`），等相关初始化完成后再布局所需容器。方向和居中修复不能以提前执行根布局为代价；网页就绪时布局网页自身容器，与启动期强制根布局分别处理。

## 全程一个 Loading、一个位置

| 项目 | 01 默认值 |
|---|---|
| 方向 | 系统启动页、Loading 与默认网页为竖屏；回退游戏恢复原生契约 |
| 背景 | 不透明纯黑，覆盖全屏并阻止点击穿透 |
| 内容 | 只有一行 `Loading…`；不另外显示转圈图标、进度条或第二份文字 |
| 位置 | 完整屏幕/根视图的几何中心；不是安全区中心，也不是“图标＋文字组”的中心 |
| 字体 | iOS 系统字体，Regular，17pt，白色 |
| 文字层 | 系统 LaunchScreen 与运行期原生层交接；iOS 的 Unity 遮罩只画黑底，不画 Loading 文字 |

系统启动页与原生标签使用完全相同的文案、字体、字号、颜色和根视图中心约束。不要让 LaunchScreen 按屏幕居中、运行期却按 safe area 居中；不要给某一阶段单独加 spinner，导致文字在组内向下移动。Editor 或其他没有原生覆盖层的平台可以显示 Unity 文字，但 iOS Player 编译分支必须去掉这份文字。

### 在首帧前遮住游戏

只暂停游戏数据加载或等待接口，**场景美术仍可能被渲染**。启动协调器必须在首场景第一帧之前建立黑色覆盖层，例如在 `RuntimeInitializeOnLoadMethod(BeforeSceneLoad)` 中创建常驻、高排序的全屏 Canvas，同时建立原生不透明黑色覆盖层。也可复用项目已有的独立启动场景，避免同时引入第二套 UI。游戏初始化、音频和输入按路由结果启动。

Unity 的黑色覆盖层覆盖所有角落并拦截 UI 输入；网页成功后可以继续作为 WebView 底下的黑色背景。避免为了隐藏游戏而全局暂停 `Time.timeScale`，从而把授权、超时或回退流程一起暂停。

### 系统启动页也要一致

- LaunchScreen 使用单行 17pt `Loading…`，约束到根视图 `centerX`/`centerY`，背景黑色。
- 同时设置 `UILaunchStoryboardName` 和导出中存在的 `UILaunchStoryboardName~iphone`、`~ipad`、`~ipod`。只改通用键可能仍被设备专用键覆盖。
- 把实际 storyboard 加入主 App target 的 Resources；不能只写 Info.plist 而漏打资源。
- 用户要求从系统启动到 SDK 期间统一黑底时，处理 Unity 自身的启动画面，避免它插在两层 Loading 之间。按所用编辑器支持的设置关闭或统一背景，不绕过版本或授权限制。
- 测试包升级时使用可辨识的构建版本，核对手机装的是本次包；系统启动页缓存或旧包不能被误认成源码未修改。不要默认卸载并清空用户数据来处理缓存。

### 覆盖 Unity 启动动画

用户要求系统启动到业务切换始终显示 Loading 时，覆盖的是整条启动链。C# `Awake`、`BeforeSceneLoad` 或首场景执行时，Unity 的启动动画可能已经开始；`PlayerSettings.SplashScreen` 设置也不能单独证明实际画面没有 Logo。按编辑器和授权支持的设置处理启动画面，不修改许可校验或引擎二进制。

- 按本 Unity 版本的生命周期，在启动动画首帧前挂上原生不透明遮罩，例如确认 `preStartUnity` 处于引擎绘制之前；在 `showGameUI` 等视图交接点保持覆盖。沿用已有 AppController/SDK 生命周期，不为挂 Loading 覆盖掉归因或 FB 的代理实现。
- 根视图中的 `topmost=true` 只说明同一个父视图内的顺序，不能证明高于 Unity 的启动窗口。若 Loading 与 Unity 动画仍共存，核对真实窗口和层级；可用同一 `UIWindowScene` 中高于 Unity 内容窗口的独立不透明窗口覆盖。根据现场验证选择层级，不把某台设备的数值固化成所有工程的固定值。
- **独立 Loading 窗口保持非 key**：不要调用它的 `makeKeyAndVisible`；API 支持时在窗口子类覆写 `canBecomeKeyWindow` 返回 `NO`，阻止系统把它选成 key，并实测 `isKeyWindow`。焦点留给业务窗口，系统授权仍可交互。仅“不主动 makeKey”不足以证明不会抢焦点；页面停住、Update 不推进或应用失去前台时同时核对焦点和生命周期日志，不能无限留黑屏。
- 遮罩铺满窗口、纯黑不透明、只有一份居中文字，系统启动页与运行期复用相同外观。不能强制早期 Unity 根视图布局来居中，避免触发键盘初始化断言。覆盖窗口沿阶段规则选择方向，不能借此永久锁死 H5 显式旋转或改变游戏原方向。
- HTTP 返回、拿到 URL、引擎首帧都不是撤层时点。只由本次网页导航的就绪回调或原生游戏及方向布局就绪撤层；失败回退时保持/恢复覆盖，使旧回调失效。重复显示不新建第二份文字，隐藏后窗口不继续挡住 H5 输入。

验证时分开记录：原生遮罩是否在 Unity 绘制前创建、是否高于实际 Unity 窗口、标签数量、是否意外成为 key、何时及因何撤层。上述状态用于定位；“Unity 动画不再露出”仍要依据本次真机冷启动的画面，不能再次仅凭状态字段宣布成功。

## 什么时候可以撤掉覆盖层

| 当前阶段 | 显示行为 |
|---|---|
| ATT、SDK 初始化、归因等待、入口请求 | 黑底单一 Loading，游戏不可见 |
| 业务成功且下发有效 URL | 仍然 Loading；开始在覆盖层后加载网页 |
| 当前网页已完成加载、布局与首帧准备 | 在主线程一次性交接到网页，移除原生 Loading |
| 入口失败、空 URL、网页错误/超时/进程终止 | 保持或恢复 Loading，清理网页，选择原生游戏 |
| 原生游戏数据和界面已经准备好 | 才撤掉黑色覆盖层并显示游戏 |

拿到 URL、HTTP 200、SDK 初始化回调和 `Show` 调用都不是撤掉 Loading 的依据。回退时也不能仅因为 `state = native` 就露出还未准备好的游戏。

自建 WKWebView 的一种实现：让网页保持可渲染状态，放在不透明黑色覆盖层后；当前导航的 `didFinishNavigation` 后等待网页连续两个 `requestAnimationFrame`，再由主帧携带本次随机 token 回到原生，完成布局后揭开覆盖层。它是首帧同步手段，不代替截图/录屏验收；采用其他 WebView 插件时使用其实际可用的渲染就绪机制。不要先把 WebView `hidden` 或从窗口移除，再无限等待可能被节流的绘制回调。

保持以下生命周期约束：

- 用当前 `WKNavigation`/导航代次与 readiness token 关联加载；同一个 WebView 上的旧导航也可能晚完成。只检查 WebView 实例不够。
- 只接受当前可信主帧的就绪回调；页面的任意字符串消息不能直接关闭 Loading。
- 新导航开始、关闭网页和失败回退时使旧 token 失效；旧成功、旧失败和旧超时均不能覆盖新路由。
- 授权、归因、请求、网页等待各自有上限；总启动截止时间是最后兜底。取消/回退后，协程在恢复时也不得重新请求入口或露出网页。
- 兜底幂等。网页加载失败、主文档 HTTP 4xx/5xx、无内容响应以及渲染进程终止都应到达明确终态。

## 网页刘海与 Home Indicator 适配

本默认方案让**网页内容在系统安全区内显示**，屏幕边缘仍为黑色。Loading 文案的“屏幕中心”与网页的“安全区边界”是两套不同约束。

1. 原生宿主容器铺满父视图，随根视图尺寸变化；容器、WKWebView、scroll view 和 under-page 背景在第一次加载/显示前都设为不透明黑色。
2. WKWebView 四边分别约束到宿主容器的 `safeAreaLayoutGuide`。不要固定写 `top = 59`、`bottom = 34`，也不要按某台设备的分辨率计算刘海高度。
3. WebView frame 已在安全区内时，可设 `contentInsetAdjustmentBehavior = Never`，避免 UIKit 再加一轮 inset；这是配套选择，不是对所有 WebView 一律关闭安全区。核对网页已有 viewport/CSS，避免再叠加同一份安全区 padding。
4. 使用 Auto Layout 或等效的实时布局机制，在旋转、窗口尺寸与 safe-area 变化后重新布局。仅创建时设置一次 `frame = parent.bounds` 不构成刘海适配。
5. 将容器加入真实窗口后读取安全区，在揭开 Loading 前完成布局。比较 WebView frame 和 safe-area layout frame 时统一到同一个坐标系。
6. 方向回调中的 Refresh 不得再赋值 `web.frame = parent.bounds` 覆盖安全区约束；关闭/替换网页同时移除宿主，避免黑色空容器挡住回退游戏。

旋转按钮和运行期方向模式另按 [方向契约](webview-orientation.md) 验证；安全区 frame 正确不等于按钮指令已接通。

若当前产品明确要求网页背景延伸到刘海、由 H5 负责安全区，则采用其既有 `viewport-fit` 与 `env(safe-area-inset-*)` 契约，并确认内容仍可访问。不要在不核对 H5 的情况下同时缩小原生 frame、修改 CSS、裁掉内容来消除黑边。

## 验证范围与证据

- 状态测试覆盖：启动不露游戏、拿到 URL 不撤遮罩、网页就绪才显示、回退等游戏准备好、旧回调不能重开页面；同时检查 Unity 覆盖层确实全屏、不透明并拦截输入。
- iOS 包内确认 Unity 的 Loading 文案分支已排除，原生视图树只有一个可见标签、没有额外 spinner；启动页各设备专用键和打包资源一致。
- 真机冷启动分别核对系统启动/Loading 的竖屏首帧、默认网页竖屏及实际可控失败分支的原生方向恢复；原生横屏项目应得到“竖屏 Loading → 竖屏网页；失败回退 → 横屏游戏”。记录本次 runId、真实窗口方向/尺寸、Unity `Screen.orientation`/宽高和原生开关，不能只核对设置值或网页最终画面。有已约定的 H5 显式旋转功能时另测其按钮链路。测试驱动必须显式触发，普通包不自动旋转、不加载测试页。
- 记录实际标签数量、坐标、根视图 bounds、屏幕 scale、WebView frame 与安全区；各 Loading 阶段的位置应一致。UIKit 像素对齐可能带来不足一个物理像素的偏差，应使用本次实际 scale 换算容差，不把 `0.1pt` 等武断阈值当作视觉差异，也不放宽到可见位移来掩盖问题。
- 几何日志可证明数量和布局，不能独立证明 Unity 动画已完全遮住或交接没有闪烁。任务包含视觉验收时，先确认实际前台为目标 App，再采集从系统打开、Unity 初始化、请求等待到网页/游戏就绪的画面；工具只在后台 launch 不能当作完成冷启动验收。仅保留本次授权测试相关画面。连续截图须带时间戳并说明采样空档，不能当作逐帧录屏或用稳定截图证明所有中间帧。
- 分别报告状态/编译验证、原生几何验证、真实画面与旋转验证；没有取到的证据保持未验证，不补造截图或测量值。具体交付边界见 [验收参考](verification.md) 和 [交付收尾](delivery.md)。
