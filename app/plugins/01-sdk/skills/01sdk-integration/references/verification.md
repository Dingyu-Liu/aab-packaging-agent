# 验证与结果判读

## 证据层级

| 证据 | 可以说明 | 不能单独说明 |
|---|---|---|
| Editor 编译 | 当前编辑器可加载代码 | native 库能在 iOS 链接 |
| Editor/Device Simulator 运行 | 对应平台分支和本地游戏正常 | iOS SDK 或入口请求已执行 |
| 实际 UniWebView 中运行测试 HTML | JS → native → JS 消息往返 | 普通浏览器/mock 等同于原生桥 |
| iOS 构建、签名、安装 | 产物可构建和安装 | 手机已经启动且测试通过 |
| 启动命令返回成功 / PID | 系统接受了本次启动请求 | 应用已持续运行、Loading 正常交接或页面已就绪 |
| 本次真机报告 | 记录覆盖的设备行为 | 其他设备/网页也无问题 |
| SDK 初始化 / queued | SDK 已初始化 / 接受调用 | 请求已送达或入库 |
| SDK HTTP 200 | 所记录请求得到 HTTP 成功响应 | 已对应到本次事件、归因正确或控制台已收数 |
| 入口 HTTP 200 + 业务签名错误 | 已收到接口响应，业务验签失败 | 成功获得入口 URL |
| 业务成功 + 有效 `data.spare_url` | 本次请求被接受且后台下发地址 | 网页已加载或 SDK 后台归因正确 |
| 本次返回 URL 与 WebView 加载成功状态关联 | 本次下发网页已经加载 | 页面全部功能或后续事件已经验收 |
| 后台事件记录和归因验证 | 经过关联核验的后台行为 | 未测的其他业务链路 |

正式入口 DNS/网络失败不阻止本地测试页验证，但业务入口仍未打通。SDK 商家接口与业务入口是不同服务，不能相互代替验收。

有已配对真机时，独立测试包安装到真机是默认验收路径；模拟器运行只在没有可用设备或用户明确要求时进行，且模拟器结果不能替代真机结论。

## Facebook 事件验收

先按 [Facebook 配置、事件与 TLS](facebook-events.md) 核对 Resources 持久化、实际签名包配置、初始化后的 App ID 和真实请求。正确 Info.plist 不能排除稍后被 Unity 默认 ID 覆盖；只读应用查询 200 不能代替真机事件验证。

| 本次证据 | 能得出的结论 | 仍不能得出的结论 |
|---|---|---|
| 实际 `FB.AppId` 与 `/{appId}/activities` 匹配 | SDK 使用了正确应用身份 | 请求已发送成功或后台入库 |
| 激活事件出现在 SDK 日志中 | 对应事件进入 SDK 流程；需区分缓存批次 | 本次新事件已经送达 |
| `Flush Result : No Connectivity` 或 TLS -1200 | 该次发送/安全连接失败 | SDK 未初始化、全部配置正确，或某个具体后台必有故障 |
| 关联本次事件的 SDK 成功发送结果 | 对应批次有成功发送证据 | 广告归因与后台事件已核验 |

保存 runId 与观察时间范围；日志继续追加时不能沿用先前计数冒充完整采集结果。代码身份修复与网络恢复分别记录，网络失败时保留后台未验证状态。

## 正常启动证据

安装回执、launch 请求、运行就绪分别记录。安装已成功但启动失败时保留 `installed=true`；命令返回成功只记启动请求成功，不能直接记 `normalStartupVerified=true`。在任务授权包含真机验证时，使用当前 Bundle ID、构建号、启动请求时间与本次 runId 关联运行状态，确认实际到达网页首帧就绪或原生游戏场景及布局就绪。旧状态文件、仅“与上一次不同”的报告和短暂 PID 均不足以证明本次就绪。

脚本消费 Unity 的 `DateTime.ToString("o")` 时，要能解析带时区的七位小数秒时间戳；旧版 Python 可能需在保留时区的前提下规范化精度，再与启动请求时间比较。不要把解析失败吞掉后笼统报应用无响应，也不要删除时间校验来通过。

进程后续消失时先取本次 console/崩溃堆栈，区分加载器失败、原生递归、系统终止、切后台和正常退出。退出码 0 不足以判正常启动，也不能单凭退出或断连断言崩溃原因；正常启动尚无证据时保持未验证。当前 `.app` 的动态依赖与 Objective-C 方法冲突排查见 [原生启动故障](ios-device.md#原生启动故障与包内依赖)。

Loading 验收同时核对原生遮罩创建时点、实际窗口层级、焦点、单份标签和最终就绪撤层；功能状态与画面证据分别记录。截图采样只证明已捕获的时点，缺少完整区间或失败分支画面时写明范围。详见 [覆盖 Unity 启动动画](startup-presentation.md#覆盖-unity-启动动画)。

## 启动与回退测试

覆盖当前项目需要的情形：有/无归因、归因超时、授权允许/拒绝/晚于等待、缓存命中/失效、入口空值/失败、网页失败/进程终止。需要断网等外部条件时使用本地受控替身或明确的测试设置，不随意断开用户整机网络。

方向必须按阶段验收：系统启动/Loading 为 Portrait，默认网页为 Portrait，失败或关闭网页后恢复原生游戏原方向及全部自动旋转开关。原生横屏游戏要覆盖“竖屏启动/网页 → 失败回退横屏 → 再冷启动回到竖屏网页”；固定竖屏及 AutoRotation 游戏分别按原配置判断。若构建时覆盖为 Portrait，核对独立随包原方向配置确实来自覆盖前的游戏设置，运行期不能把启动覆盖值当作原值。记录本次 runId、实际窗口方向/尺寸、Unity 方向/宽高和允许 mask；API 请求成功、方向回执或配置常量不能代替这些观察。没有设备证据时如实保留未验证状态。

发生异常时先复现和定位再修复。状态、错误码与结果中不能输出密钥、完整归因标识或签名原文。支持脱敏状态输出；原始请求需要诊断时保存到本任务受控位置并避免在共享报告中展示。

## 签名迁移回归

签名故障排查顺序、脱敏案例及配置比较工具见 [接入参考的签名规则](integration.md#签名规则)。至少覆盖 YAML 外层单引号/双引号、转义、合法内嵌引号、前后空格、Unicode、非字符串和解析失败时不泄露值。不要以统一去引号或固定密钥长度来“修复”配置。签名回归还要覆盖请求体与签名原文同序：嵌套对象（尤其 `appsflyer`）的键顺序必须与签名时的递归排序一致；Editor 空归因探测（`appsflyer` 为 `""`）不覆盖这一项，需用带真实归因的真机请求验收。

本 skill 的 `tests/test_signing_key.py` 使用合成密钥检验真实解析和 CLI 退出码；依赖已就绪时运行：

```sh
python3 -m unittest discover -s tests -v
```

文件对比只能证明迁移一致。完成接入仍需保存与本次启动关联的业务返回；`ret` 的成功取值按当前接口契约判断，`data` 是错误文本时不能当成含 `spare_url` 的对象。无响应时记录 null/空正文，不拼造服务器 JSON。

## 单一 Loading 与安全区验收

实施规则见 [启动显示与刘海安全区](startup-presentation.md)。先核对系统启动/Loading 与默认网页的实际竖屏，以及回退游戏是否恢复原方向。其他显示项分别检查：系统启动页与原生标签文案/字号/屏幕中心一致；iOS Unity Player 不再绘制第二份文字；网页首帧前游戏不可见；失败时 Loading 保持到游戏准备好；WebView 四边在实际安全区内并随旋转重排。

标签数量、坐标和原生 frame 的日志只支持几何结论，不能代替无瞬态重影/闪游戏的画面证据。使用实测屏幕 scale 解释像素对齐误差，明确区别“固定位置”“安全区坐标匹配”和“连续画面无闪烁”。可将结论记录到输入模板的 `startupPresentation.verification`，未测项保持 false/null。

## 白边、首次显示与旋转过程

先检查显式测试干预：旋转脚本、颜色 A/B 对照、JS 注入和恢复逻辑。记录中若有主动设置白色背景，先从普通包中移除测试器，再判断是否仍有产品缺陷，不能把对照测试本身误报为 SDK 问题。

产品要求黑边时，在 WebView 首次 Load/Show 前显式设为不透明黑色。若仍有白边，逐层核对 WebView、scroll view/under-page 背景、宿主容器、safe-area/content inset、H5 html/body/CSS 和 viewport 设置；定位后修对应层，保留完整 Frame 和页面内容，不靠裁边掩盖问题。模板 CSS 不是原生背景设置的替代品。

验证冷启动第一次页面显示、第一次左右横屏、旋转中间帧、回竖屏和再次横屏。使用真实包含 WKWebView 的窗口截图/录屏；Unity 的 Texture2D.ReadPixels 可能仅包含游戏渲染，不能证明原生网页外观。稳定后的截图和成功方向回执不能证明无瞬态闪白；只有稳定截图时明确报告该范围。QA 的白/黑对照截图与普通包截图分别标注，不能混用为普通启动证据。

## 方向与尺寸

用户报告某个按钮无效时，按 [实际网页方向契约](webview-orientation.md) 读取该按钮 handler/参数，复测同一个 DOM 按钮经过原消息通道的行为。native 调用或规范值注入不能替代按钮验收。先测自然安全区布局，再检查显式刷新；不在断言前修正 frame。

分别验证“接受指令”和“实际完成”：在有上限的等待内核对目标方向、Screen 宽高、native Frame、JS innerWidth/innerHeight、devicePixelRatio、safeArea。支持哪些方向由项目决定。

全屏 WebView 下，不能要求网页 CSS 宽度等于屏幕像素，也不能只比较全屏纵横比。默认 WKWebView 视口可能避开刘海/状态栏：

- 屏幕 `2796 × 1290`、DPR=3、安全区宽 `2442`，网页 `814 × 430` 可为正常横屏布局。
- 首先要求原生方向与请求一致、Frame 与预期匹配。
- 在没有缩放/工具栏等额外布局因素的测试页中，CSS 各维度应落在安全区/DPR与全屏/DPR之间，允许少量取整误差；横竖方向仍须一致。
- 陈旧的竖屏视口、越界尺寸、零 DPR 不能通过。嵌入式 WebView、页面缩放或工具栏需使用对应的实际 frame 约束，不能照搬全屏判据。
- 快照只证明采集时的网页内容；要声明恢复后的网页布局也正常，恢复方向后仍需等待 JS 视口重排。它不等同于整台手机当前屏幕。

## 报告新鲜度

首选本次 launch 生成的 runId，并写入 app 报告。无法传入 runId 时，记录 UTC 启动请求时间，与 `startedAtUtc` 比较，并检查 `finishedAtUtc >= startedAtUtc`。只比较“与上一份报告不同”会漏掉用户另外手动运行产生的旧报告。只按本机复制时间或文件 mtime 也不可靠。

已知设备时钟偏差应单独记录，不能通过无限放宽时间范围接纳旧结果。等待新报告有上限；失败应保留实际状态，不反复安装碰运气。后续重试应有新的证据或状态变化。

## 附带工具

命令从本 skill 目录执行；项目/编辑器路径按本机实际值填写。

```sh
python3 scripts/inspect_unity.py --project /path/to/project --editor-app /path/to/Unity.app
```

只读输出项目版本、两个模块位置、SDK目录、入口脚本候选和脱敏包依赖。脚本不证明 Editor 已加载模块，也不替代代码阅读。

对于与本参考 schema 一致的全屏设备报告：

```sh
python3 scripts/check_device_report.py /path/to/results.json --not-before "$LAUNCH_UTC" --expected-cases 16 --orientations portrait landscape-left landscape-right
```

当前附带网页为 16 个用例；旧版或自定义网页按实际协议显式设置数量，不为通过检查伪造/补齐结果。

`LAUNCH_UTC` 必须是启动本次 app 前立即记录的实际 UTC/时区时间，不能使用示例旧时间。可加 `--output /path/to/summary.json`。脚本默认最多容忍 3 秒时钟差，检查唯一用例计数、严格布尔通过状态、三种方向及实测安全区尺寸，失败退出码为 1，输入错误为 2。

必要报告字段：`startedAtUtc`、`finishedAtUtc`、`phase`、`outcome`、`cleanupCompleted`、`webReport.cases`、`orientations[].viewport`、`orientations[].javascriptViewport`。SDK诊断支持 `diagnostics.appsFlyerInitialized/facebookInitialized/afLastSessionResponseCode/afLastEventResponseCode`。不要为了适配检查器伪造不存在的证据；不同报告 schema 应明确转换或直接检查真实数据。

摘要不复制设备归因 ID，SDK 状态的 `evidence_from_current_run` 标明是否来自本次运行；旧报告中的 200 只能作为历史信息。摘要始终把商家控制台和正式入口契约标为未独立验证。后台验收需要单独提供相应证据。

## 最终交付

先执行 [自动测试隔离与交付收尾](delivery.md)。QA 通过不等于普通包已交付；当前源码、交付 ZIP 和手机已安装包各有独立证据。不要把只有元数据/二进制检查的结论升级为真机冷启动验证。

给出已改变的工程/测试包、实际通过项和未验证项，附本次脱敏结果及必要截图。只在确有实际证据时使用“通过”。记录残余域名问题、协议假设、签名到期时间等与交付有关的限制，不增加无关发布流程。
